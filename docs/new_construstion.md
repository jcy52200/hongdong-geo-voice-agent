在采纳 Siphon 作为媒体桥接层之后，整个系统的架构需要围绕一条新的主线来组织：**控制平面负责“打给谁、何时打、打完做什么”，Siphon 负责“把电话音频原样送进模型、把模型音频原样送回电话”，豆包 Seeduplex 负责“对话本身”**。下面按一通外呼从发起到结束的完整数据流，逐层展开。

---

### 第一层：外呼任务与槽位调度（控制平面）

一通电话的起点不是 SIP 信令，而是**一个被判定为“可以拨出”的决策**。

**1.1 槽位池的定义**

在端到端架构下，“坐席”不再对应真人，而是一个**可用的端到端会话槽位**。一个槽位由三件事共同决定是否可用：Siphon 桥接实例有空闲的 WebSocket 连接容量、豆包 Seeduplex 的并发配额有余量、以及业务侧允许该任务在当前时段发起外呼。控制平面维护一个实时的**槽位池**，每个槽位的状态在“空闲 → 占位拨号中 → 通话中 → 释放”之间流转。

**1.2 预测式拨号策略**

控制平面根据历史接通率动态决定**超额拨号倍率**。最保守的起点是**比例策略**：如果历史接通率为 30%，则拨号倍率设为 1/0.30 ≈ 3.3，即每 1 个预测即将空闲的槽位，同时发起约 3.3 通外呼。当系统积累了足够的本线路接通率和平均通话时长数据后，可以切换到 **PID 模型**：输入目标呼损率和历史接通率做冷启动，运行中根据实时槽位释放速率持续调整拨号节奏，目标是让槽位利用率稳定在 85%–90% 区间。端到端模型的单路资源消耗高于纯文本 LLM，**起步阶段建议将倍率上限设为 3:1，经过 P95/P99 压测后再逐步放宽**。

**1.3 与合规外呼时段的硬约束**

调度器必须在拨号前校验当前时间是否落在任务允许的外呼时段内，并执行**频次控制**（同一号码的日/周呼出上限）和**退订名单过滤**。这些检查失败时，任务不进入槽位分配，直接回队列或标记为跳过。


### 第二层：SIP 中继与呼叫发起（信令层）

槽位就绪后，控制平面通过 Siphon 发起一通外呼。Siphon 本身不直接持有运营商线路，它通过**你自有的境内 SIP 中继**将呼叫送到客户手机。

**2.1 呼叫发起路径**

控制平面向 Siphon 的控制通道发送呼叫发起指令，Siphon 通过 SIP INVITE 将呼叫路由到你对接的**持牌 SIP 中继**。中继侧完成号码鉴权、主叫号码透传和运营商落地。这里的关键合规前提是：SIP 中继必须以**公网可达的 SIP 中继方式**接入，且中继提供方需要具备相应的增值电信业务资质；如果系统涉及三方以上的通信协同，还需要确认**多方通信服务许可证**的覆盖范围。纯外呼场景下，至少需要确保中继备案信息与主体、码号、业务场景一一对应，做到可溯源。

**2.2 Siphon 在信令层的角色**

Siphon 在这里承担的是 **B2BUA 式的呼叫控制**：它接受控制平面的发起请求，向外拨出 INVITE，处理 180/200/ACK 等 SIP 状态，并将呼叫状态（振铃中、已接通、被叫忙、无应答）实时回传给控制平面。控制平面据此判断“这通电话是否值得接入 AI”——例如，被叫忙或无应答的呼叫不应占用端到端会话槽位，直接释放并触发重试逻辑。


### 第三层：Siphon 的 WebSocket 桥接（媒体桥接层，架构核心）

客户接听后，Siphon 进入 **`ws_uri` 的 Takeover 模式**。这是整个架构中唯一需要精确配置的工程环节。

**3.1 Takeover 模式的含义**

在 Takeover 模式下，Siphon 将 WebSocket 服务器（也就是你的**桥接适配服务**）作为主叫方的“对端”。它**不再执行常规的 A↔B 中继**，而是把客户侧的 RTP 音频解码为 PCM 后通过 WebSocket 上行发送，同时把 WebSocket 下行的 PCM 编码回 RTP 播放给客户。你的豆包会话服务完全不接触 RTP、抖动缓冲或编解码器，只读写裸 PCM 帧。

**3.2 必须精确对齐的音频格式**

这是整个架构中**最容易出错的一环**，需要在 Siphon profile 和豆包会话参数之间做严格映射：

| 方向 | Siphon 侧配置/行为 | 豆包 Seeduplex 要求 | 处理方式 |
|---|---|---|---|
| **上行（客户→模型）** | 通过 `ws_sample_rate: 16000` 将 G.711 的 8kHz 通话重采样为 **16kHz L16 单声道** | 16kHz，20ms 帧，**640 字节/包** | Siphon 完成重采样和帧化，桥接服务直接转发 |
| **下行（模型→客户）** | Siphon 期望收到**与上行同格式**的 PCM，然后编码回客户的 codec | 输出固定为 **24kHz** `pcm_s16le` | 桥接服务必须将 24kHz 下采样为 **16kHz** 后再写入 WebSocket |

Siphon 的 `ws_sample_rate` 是**独立于呼叫 codec 的**：一通 8kHz 的 G.711 通话可以以 16kHz 向模型推流，引擎会自动完成双向重采样。但豆包下行是 24kHz，Siphon 不会替你完成 24k→16k 的转换，**桥接服务中必须包含这一步轻量重采样**。

**3.3 打断的“最后一公里”**

豆包 Seeduplex 自身具备全双工打断决策能力，但**“停止播放”这个物理动作仍由 Siphon 执行**。当模型判定客户插话、需要中断当前播报时，桥接服务向 Siphon 的 WebSocket 发送 `{"type": "clear", "data": {"reason": "barge_in"}}`。Siphon 会清空播放队列中尚未发出的音频帧，在一个 tick 内生效，并回复 `cleared` 标记，供桥接服务同步轮次边界。如果缺少这一步，模型“决定”打断后，Siphon 仍会继续播放已排队的下行音频，客户会听到 AI 的“回声式”抢话。


### 第四层：豆包 Seeduplex 会话生命周期（模型交互层）

桥接适配服务在 WebSocket 建连后，需要管理豆包会话的完整生命周期。

**4.1 会话创建与业务上下文注入**

建连后首先发送 `session.create`，其中必须包含 `session.audio` 的输入输出格式（16kHz 输入 / 24kHz 输出）。业务上下文通过 `session.instructions` 注入，包括本次外呼的场景、角色人设、合规话术要点和禁止事项。不同外呼任务（催收、回访、营销）使用不同的 instructions 模板，由控制平面在发起呼叫时传入桥接服务。

**4.2 工具调用的异步闭环**

`session.tools` 以标准 JSON Schema 声明工具集，由模型在对话中自主决策何时调用。桥接服务收到 `response.function_call_arguments.done` 后，**不应在音频桥接的同步路径中直接执行耗时业务操作**，而是将工具调用请求投递到控制平面的**异步工作队列**，由控制平面执行 CRM 查询、订单检索或转人工请求，再将结果通过 `session.update` 或对应的事件回送给模型。豆包的工具调用下行事件中 `items` 是数组结构，需要逐项读取 `call_id`、`name` 和 `arguments`，不能假设为单次调用。

**4.3 音频节奏与保活**

豆包要求上行音频**严格按实时节奏发送**，发送速率偏离实际节奏会触发服务端错误。桥接服务不能“尽可能快”地灌入音频，而需要按 20ms 时钟节拍从 Siphon 的 WebSocket 接收并转发。当客户长时间静音时，仍需发送静音帧或 `input_audio_mute.commit` 事件维持模型侧会话；同时建议每隔 10 秒发送静音包以保持与平台的连接，超过 90 秒无静音包平台可能释放连接。


### 第五层：通话结束与会话收尾

**5.1 正常结束路径**

当模型判定对话完成、或客户挂断、或控制平面触发结束时，桥接服务依次执行：发送 `session.close` 等待 `session.closed` 确认（避免直接断开触发 ContextCanceled），向 Siphon 发送 `stop` 结束桥接，Siphon 释放 SIP 呼叫腿。控制平面将槽位标记为释放，并根据通话结果（意向等级、工具调用产出）更新任务状态。

**5.2 转人工的衔接**

如果模型通过工具调用请求转人工，控制平面在接到请求后，需要将 Siphon 中的当前呼叫腿**重桥接到一个人工坐席的分机或软电话**。由于 `call_id` 从 Siphon 发起呼叫时就已贯穿全程，转接后人工坐席的桌面可以直接加载本次 AI 对话的完整记录（可通过 Siphon 的 `ws_tee` 旁路复制或控制平面侧的对话日志获得），客户不需要重复描述问题。


### 第六层：数据层与可观测性

**6.1 必须持久化的数据**

- **通话记录（CDR）**：call_id、主叫/被叫、开始/结束时间、通话时长、结束原因、使用的槽位和 SIP 中继链路。
- **对话元数据**：session id、instructions 模板标识、工具调用序列（call_id、name、arguments、result）、转人工标记。
- **音频**：是否录音取决于合规要求；如果录音，建议通过 Siphon 的 `ws_tee` 旁路获取，避免在桥接主路径中增加额外负担。

**6.2 关键监控指标**

Siphon 暴露了 `siphon_b2bua_calls_active` / `siphon_b2bua_max_concurrent_calls` 等并发指标，建议在活跃并发/上限 **> 0.8** 时触发告警。此外需要监控：豆包会话的建连成功率、P95 首字音频延迟、打断 `clear` 的生效延迟、以及桥接服务的重采样队列深度（队列持续增长意味着下行音频消费速度跟不上模型输出速度，需要背压）。

### 需要前置验证的两个工程点

**第一，Siphon 的桥接模式与 `ws_uri` 的配合。** 官方文档中的 `voice_ai.md` 示例主要展示的是 `ws_uri` 的 Takeover 行为，但桥接服务作为 WebSocket **服务端**还是**客户端**，取决于 Siphon 的配置方向。从文档看，`ws_uri` 是 Siphon “dial 那个 URI”，即 Siphon 作为 WebSocket 客户端去连接桥接服务。这意味着桥接服务需要先启动并监听，Siphon 在呼叫接通后主动连接过来。建议在测试环境中用一通真实 SIP 呼叫验证：Siphon 是否按预期发起 WebSocket 连接、首帧 `start` 消息中的 `sampleRate` 是否与 `ws_sample_rate: 16000` 一致、以及 `clear` 发出后 `cleared` 回复是否在一个 ptime 内返回。

**第二，豆包会话的并发配额与 Siphon 槽位池的对齐。** 控制平面的槽位池上限必须取 **Siphon 桥接容量**和**豆包并发配额**的较小值。在压测中应分别确认：Siphon 单实例在 16kHz 重采样和 WebSocket I/O 下的稳定并发路数，以及豆包账号在当前配额下的建连成功率和 P99 延迟表现。两者中任何一个成为瓶颈，都应通过增加桥接服务副本或申请豆包配额提升来解决，而不是让呼叫在中间层排队超时。
